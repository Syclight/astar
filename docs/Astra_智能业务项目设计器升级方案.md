# Astra 智能业务项目设计器升级方案

版本：v0.1（设计提案）｜日期：2026-09-05

## 1. 升级目标

在现有 Agent 工作流运行时之上，增加业务设计、能力复用和项目生成能力，实现以下闭环：

**业务目标 → 项目蓝图 → 配置与 Agent 生成 → 校验 → 试运行 → 验收。**

用户通过自然语言描述目标，系统生成可解释、可修改、可验证的业务项目。现有 `project.yaml`、`configs/workflow.yaml` 和 `ProjectRuntime` 继续作为项目与执行基础。

## 2. 当前基础与新增范围

现有基础包括串行阶段编排、Extension、工具与 Hook 加载、独立运行上下文、检查点恢复及离线回归测试。

本次新增业务设计器、项目蓝图、能力目录、Agent 生成器和生成项目的验证闭环。现有检查点不提供外部操作的事务保证；进程退出前尚未保存的操作可能重放，业务写入仍需幂等控制。

## 3. 目标架构

| 模块 | 职责 | 输出与边界 |
|---|---|---|
| 业务设计器 | 理解目标，识别缺失信息，拆分阶段与职责 | 生成项目蓝图；不直接执行业务副作用 |
| 能力目录 | 登记和检索可复用的 Agent、工具与模板 | 提供能力标识、版本、数据契约及权限要求 |
| 项目生成器 | 将已校验蓝图转换为项目文件 | 确定性生成 YAML；保持配置与蓝图一致 |
| Agent 生成器 | 根据数据契约实现缺失能力 | 优先复用，其次生成提示词和配置，最后生成 Python 代码 |
| 验证器 | 检查配置、契约、依赖和执行结果 | 输出结构化问题与验收结论 |
| 运行控制层 | 提供工具解析、权限检查、执行记录与恢复 | 基于现有运行时演进；不自行改变业务目标 |

业务设计器决定“做哪些步骤”，Agent 生成器决定“步骤如何实现”，运行控制层负责“按约束执行”。三者共享蓝图，避免重复规划。

## 4. 项目蓝图与生成契约

新增 `blueprint.yaml` 作为设计的统一来源，至少包含：

- **目标与验收**：任务描述、交付物、成功条件、样例输入和预期结果。
- **输入与资源**：数据来源、格式、路径及必需配置。
- **工作流**：阶段顺序、Agent 职责、条件路由和失败处理。
- **数据契约**：每个 Agent 的输入、输出 JSON Schema，以及上下游字段映射。
- **能力与约束**：引用的 Agent 和工具版本、权限范围、执行预算与超时。

蓝图校验通过后，再生成 `project.yaml`、`configs/workflow.yaml`、Agent 配置或实现、提示词和测试。保存蓝图版本、能力版本及生成记录，便于定位变更来源。

蓝图变更应重新校验关联文件；检测到人工修改时展示差异，不静默覆盖。

## 5. 能力复用与运行控制

能力目录统一描述 Agent 和工具，但保留类型及调用差异。每项能力记录唯一标识、版本、用途、输入输出结构、依赖、权限和副作用类型。

设计器先检索能力目录，再判断是否需要生成。运行控制层根据明确的能力标识与参数执行调用；仅在预先允许的候选能力中动态选择，并记录实际选择结果。

采用统一管理入口，同时保留结构化调用契约。首版不引入仅接收自然语言、可任意规划和调用工具的万能接口，也不允许自动扩大工具权限或新增业务步骤。

## 6. 生成、验证与修正流程

1. **需求确认**：整理业务目标、输入资源和验收标准；关键条件缺失时请求补充。
2. **蓝图设计**：匹配已有能力，明确阶段、数据契约和执行约束，展示设计摘要。
3. **项目生成**：生成配置、提示词及必要实现，将新增能力登记为待验证状态。
4. **静态校验**：检查 YAML、Schema、能力引用、路由、依赖和权限声明，不导入生成代码。
5. **隔离试运行**：使用样例数据执行，记录成本、结果和错误；生成代码在受限环境中加载。
6. **有限修正**：区分配置、实现和需求问题，仅修正相关内容；达到预算或次数上限后停止并报告。
7. **业务验收**：按预设条件检查交付物，输出可运行项目及验证报告。

结构合法、流程完成和业务合格分别记录。LLM 评价可辅助判断，但不能替代可计算的断言、事实核验或必要的用户验收。

## 7. 首版范围与实施阶段

首版面向本地文件分析与报告生成：采用串行工作流、已有工具白名单和配置型 LLM Agent。任意 Python 代码生成、并行编排、远程部署及运行时自修改暂不纳入首版。

| 阶段 | 交付内容 | 通过条件 |
|---|---|---|
| M1：设计与契约 | 蓝图 Schema、能力目录、需求澄清和设计摘要 | 固定样例能形成完整蓝图；缺失输入和无效引用可被识别 |
| M2：项目生成 | YAML 生成器、配置型 LLM Agent、提示词模板 | 生成项目可加载；上下游数据契约一致；不覆盖人工修改 |
| M3：执行闭环 | 静态校验、受限试运行、修正预算、验收报告 | 样例端到端通过；失败可定位、恢复；修正过程有界 |
| M4：后续扩展 | 受限代码生成、能力版本治理、按需动态路由 | 在独立评估和权限机制完善后逐项开放 |

建议首个样例：**读取客户反馈文件 → 分类 → 统计高频问题 → 生成改进建议报告。**

## 8. 验收标准

- 同一蓝图可稳定生成结构一致的配置，项目通过静态检查与运行时加载。
- 生成项目通过样例数据和业务断言；缺失输入、非法输出及无效路由均有明确错误。
- 恢复执行保留历史，跳过已保存成功的 Agent；多项目工具、模型、Hook 和日志不串用。
- 工具调用受到声明权限约束，修正次数、执行时间和费用均有上限。
- 蓝图、生成文件、能力版本与执行报告能够关联追溯。
- 原有离线回归测试继续通过；新增确定性测试使用模型替身，真实 LLM 评估单独执行并记录通过率和成本。

## 9. 设计参考

参考 [Control Plane as a Tool](https://arxiv.org/html/2505.06817v1) 的能力管理与工具路由分离思路。该文属于架构提案，未给出量化验证；本方案保留 Astra 显式工作流，以实际测试评估动态路由的收益。

MCP 可作为后续外部能力接入协议，与应用运行控制层互补；连接协议与业务编排的职责应保持清晰。参见 [MCP 架构规范](https://modelcontextprotocol.io/specification/2025-03-26/architecture)。
