# 业务对象身份

作品、项目、档案等需要跨运行延续的对象，使用稳定的内部对象 ID；run ID 只标识单次执行。身份有三种配置方式：固定 key 保存团队共享状态；key_field 使用已有外部业务编号；object.resolve 的新建/继续模式为新对象分配编号。

## 已有业务编号

客户号、订单号、设备号等在运行前已经存在，可直接给 state.load/save 和 document.write 配置相同的 key_field/key_namespace：

```yaml
key_field: customer_id
key_namespace: customer
```

brief 端口绑定 task_input，其中 customer_id 必须是必填的字符串或整数。程序按“业务类别＋编号类型＋编号值”映射到稳定对象 ID，存放于 output/objects；字符串两端空白会去除，大小写保留，整数 1001 与字符串 "1001" 不同。客户 1001 与订单 1001 因命名空间不同而隔离。key_namespace 默认使用字段名，若以后改字段名，应显式保留原命名空间。不要用会变化或重名的标题代替外部业务编号。

load 默认允许首次没有状态，返回 found=false；require_found=true 则必须已存在已保存状态。首次登记不会询问用户是否新建，也不会让模型补造缺失编号。reset_field/reset_values 可显式清空该编号的状态或累积历史，但不改变其身份。key_path 不用于此简写模式，业务中的 customer_id 仍保留原编号。

多个节点共享身份时，也可先用 object.resolve@1 设置相同的 key_field/key_namespace，输出 object，再让下游统一接 object_context=true。解析器 require_found=true 表示只查询已登记对象；是否已有已保存状态由 state.load 的 require_found 决定。

key、key_field、object_context 是互斥的身份来源。key_field 与程序新建/继续模式不能混用。静态校验会拒绝可缺省的外部编号和模型输出决定存储 ID 的配置。

## 程序创建身份

工作流先调用 `object.resolve@1`，`brief` 接 `task_input`。`mode_field` 指向新建或继续的字段，`id_field` 指向继续时用户输入的编号字段。模式值默认是 `new` 和 `continue`，可用 `new_value`、`continue_value` 修改。新建不需要用户填写编号。

输出 `object` 使用内置 `business_object` Schema，含 `id` 和 `is_new`。ID 是 `obj_` 加 UUID；同一项目、运行和创建节点的重试复用相同 ID。继续时会校验格式和对象登记文件，不存在的 ID 直接报错。模型可以读取对象身份，不能产出 business_object。

`state.load@1`、`state.save@1` 和 `document.write@1` 设置 `object_context: true`，并将各自的 `object` 端口连接到同一个对象输出。状态节点不再配置 key/key_field/reset_field/reset_values。`state.save` 可用 key_path 把权威 ID 写入业务状态字段（例如 `/work_id`）。

两种对象身份入口均保存在项目输出目录内（固定 key 仍在 output/state）：

```text
output/objects/<对象 ID>/object.json
output/objects/<对象 ID>/state.json
output/objects/<对象 ID>/documents/manuscript.docx
output/runs/<运行 ID>/<对象 ID>/manuscript.docx
```

文档使用固定 filename 即可，不用可选的 task_input 编号拼接文件名。accumulate=true 在对象内累积正文，重复执行同一运行不会重复追加；本次运行文件保留当时的快照，对象目录保存最新版本。状态和文档分别保存，并非跨文件事务；失败运行仍应通过原有恢复机制处理。

已有团队须更新蓝图并重新生成相应配置和 Agent 实现，更新设计器不会自动修改已生成团队。已生成的旧实现不会被静默替换。

旧状态可显式迁移，原文件保留：

```powershell
uv run astra migrate-state business/my_team OLD_ID --key-path /work_id
```

命令按旧记录内的 key 精确匹配，复制状态和上一版备份，生成程序 ID 并建立旧编号别名。随后 object.resolve 的继续模式可接受旧编号或新 ID，二者解析到同一个对象。此旧编号别名与外部编号的命名空间映射不同：发现 output/state 中同编号的旧记录时，新的 key_field 入口会停止并提示迁移，避免另开一份空历史；迁移后应通过 object.resolve 的继续模式读取旧编号。再次迁移相同来源不覆盖对象；来源或迁移选项变化则报错，防止覆盖续写结果。失败运行若没有保存过状态，不能仅凭模型临时生成的编号迁移。

若有旧文档，可追加 `--document "manuscript.docx=D:\项目\output\documents\旧完整稿.docx"`（可重复指定）。文档必须位于该项目输出目录内；存在同名 `.旧完整稿.parts.json` 时，同时将累积记录迁移为 `.manuscript.parts.json`，供后续继续追加。没有累积记录的文档只复制文件，不从 docx/pdf 猜测历史分段。迁移命令仅迁移数据，不自动重写任意旧团队的业务配置；配置必须接好统一对象上下文后再续写。
