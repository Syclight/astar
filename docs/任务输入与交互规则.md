# 任务输入规范与执行前交互

业务项目保存可复用团队的能力与流程。每次运行提供具体产品、活动或素材，资料写入该次运行的 `output/runs/<id>/state.json`，不改写项目配置。原有未声明任务契约的项目仍按原方式执行。

## 项目配置

在现有 `project.yaml` 中添加：

```yaml
task_input:
  type: object
  additionalProperties: false
  properties:
    product:
      type: string
      minLength: 1
      description: 本次宣传的产品
    purpose:
      type: string
      enum: [线上活动, 电商促销, 品牌宣传]
      description: 本次海报用途
    materials:
      type: array
      items: {type: string}
      description: 可用素材的路径或说明
  required: [product, purpose]
interaction:
  on_missing: ask
  confirm_before_run: true
  questions:
    product: 这次海报宣传什么产品？
    purpose: 这次海报用于哪类宣传？
```

`task_input` 使用自包含 JSON Schema；顶层必须是 object，声明 properties 和 additionalProperties: false，字段名使用小写英文标识。每个字段声明明确的 JSON type；可用 required、enum、minLength 等限制。禁止远程 `$ref`。字段描述和交互问题是通用规则，不把用户举例的 Astra 产品名称写成默认值。程序不自动填写 Schema 中的 default。

`on_missing: ask` 在资料缺失或不符合规范时保存为 `waiting_input`，不启动任何工作流 Agent；`error` 返回 failed，供非交互调用方处理。`confirm_before_run: true` 在资料合格后进入 `awaiting_confirmation`，用户明确确认后才执行。questions 可覆盖各字段的提问，不填写时使用字段 description。额外未知字段等无法逐项修复的结构错误应修改输入文件后重新提交。

运行中还有两种暂停：`fs.cleanup@1` 在真正移动或删除前列出文件清单等待确认；`human.review@1` 把成果交给人审阅，输入“通过”继续，否则把修改意见交给后续步骤（常配合条件跳转返工）。命令行交互运行时会直接提问；也可用 `astra resume <project.yaml> <运行ID> --approve` 或 `--notes "修改意见"` 继续。Agent 不会在其他位置临时向人提问。文件或文件夹路径类资料在开始前检查是否存在，填错时会重新询问。

### 按选项才必填的字段

有模式或类型选项、某些资料只在其中一种选项下必填时，选项字段放进 `required`，按选项才必填的字段写进 `x-astra-required-when`。例如新作品必须给题材，续写必须给作品 ID 和上次的章节：

```yaml
task_input:
  type: object
  additionalProperties: false
  required: [mode]
  properties:
    mode: {type: string, enum: [new, continue], description: 创作模式}
    genre: {type: string, minLength: 1, description: 新作品的题材}
    work_id: {type: string, minLength: 1, description: 作品 ID（新建时由团队生成）}
    last_chapter_path: {type: string, minLength: 1, description: 上次章节的文件路径}
  x-astra-required-when:
    - {field: mode, values: [new], required: [genre]}
    - {field: mode, values: [continue], required: [work_id, last_chapter_path]}
```

运行时先问 `mode`，再按用户的选择追问对应字段，另一种选项的字段不问。需求访谈中说“某种模式下需要提供……”时，设计器会这样记录；字段真正可以不填时，在 description 中写明“可选”。

## CLI

```powershell
# 逐项接单；字符串直接输入，其他类型输入 JSON 值
uv run astra run business/my_project/project.yaml --interactive

# 可先提供部分资料，再补充缺失项并确认
uv run astra run business/my_project/project.yaml --input task.json --interactive

# 退出后用原运行 ID 继续，不新建任务
uv run astra resume business/my_project/project.yaml <运行ID> --interactive
```

输入 `/quit` 或按 Ctrl+C 保留等待状态。未使用 `--interactive` 时不读取 stdin；API/CLI 返回等待状态，不将其当成已完成。CLI 非完成状态退出码为 1，自动调用方可用 `--json` 获取 questions 和 input_errors。

## Python API

```python
from astra import engine

runtime = engine.load("business/my_project/project.yaml")
state = runtime.run(task_input={"product": "Astra"}, export_structure=False)
run_id = state["data"]["run"]["id"]

# task_input 是本次完整资料的替换，不是增量补丁
state = runtime.resume(run_id, task_input={"product": "Astra", "purpose": "线上活动"})
state = runtime.resume(run_id, confirmed=True)
```

调用方也可在首次 run 时提交完整资料并显式传 confirmed=True。完成后的运行不能通过替换资料变成另一单任务；应再次调用 run。运行创建时保存输入契约快照，之后修改 project.yaml 不会改变已经等待中的任务规范。

工作流通过 `state['data']['task_input']` 读取验证后的资料。生成器保留该数据键，禁止 Agent 输出覆盖它。自定义手写 Agent 应同样把它视为只读输入。

## 设计器与生成器

设计器收集的是团队服务范围、每单输入字段及收集规则，不要求提供每单具体值。需求记录和蓝图均支持 task_input/interaction；它们随版本一起确认，规划器不能改写已确认契约。

有 task_input 的蓝图可令 inputs 为 `{}`，不再强制提供固定样例文件。生成器把契约写入 project.yaml，并生成 schemas/task_input.json。配置型 LLM Agent 可使用：

```yaml
inputs: {brief: task_input}
parameters:
  input_schemas: {brief: task_input}
```

其余能力、输出端口及 Schema 仍按蓝图定义。出图由内置的 `image.generate@1` 完成（需先配置绘图服务，见 [通用能力配置与评测](通用能力配置与评测.md)）；任务输入只提供资料，不代表已经出图。

每单成果内容不同，可用 `matches_schema` 验收输出结构，例如 `{"path":"/data/copy_text","op":"matches_schema","value":{"type":"string","minLength":1}}`。这能检查非空文案等结构条件，不等于业务质量验收，也不应把某一单的示例内容固化为所有任务的 equals 条件。

设计器 `/run` 是非交互验收入口，遇到待输入任务会显示恢复命令，不会自动重试或把未执行任务报成验收失败。按提示在运行器补充资料，完成后可在设计器使用 `/run-resume <运行ID>` 验收。
