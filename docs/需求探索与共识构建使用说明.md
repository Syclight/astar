# 需求探索与共识构建

日期：2026-09-07。当前默认 `chat` 已接入需求探索层；旧版直接蓝图对话已移除，非交互的 `design` 子命令仍可使用。

## 1. 目标与职责

通过问答形成有来源、可修订、经用户确认的需求，再交给蓝图规划器。探索阶段不要求文件、不加载能力目录，也不会因为当前无法读取 Excel 或连接数据库而拒绝理解业务。

使用同一个模型的两个职责：需求探索者负责语言澄清、目标与约束分析、场景验证和共识整理；蓝图规划者负责按已确认需求匹配现有能力。程序负责保存、校验与确认，不让模型自行批准需求。

## 2. 最小使用流程

需求整理完成后输入“继续”获取团队方案，用 `/team` 查看角色分工，`/select 方案ID` 切换，最后输入“确认”一并确认。详见 [团队方案](团队协商使用说明.md)。Token 预算与用量估算功能已下线。

先按新手手册配置模型，然后执行：

```powershell
python -m astra_designer chat --session workspace/designs/payroll-discovery
```

直接描述：

```text
我想做一个月度工资核算项目。每月提供人员名单和工作情况的 Excel，计算后生成工资表，交给负责人审核。先不做实际付款。
```

按问题逐步补充字段、关联方式、计算规则、缺失记录的处理和验收标准。不需要先 `/input`；不要为了完成对话编造尚不清楚的规则。

当信息足够明确时，系统显示完整的需求条目、用户原文来源和未决事项，并提示确认版本。例如：

```text
/requirements
/confirm 3
/plan
```

`3` 必须替换为当前显示的版本号。`/confirm` 不调用模型；过期版本、仍存在阻塞事项或缺少关键类别时，不能确认。

确认后仍可以直接输入修改意见。当前确认和当前规划会失效，系统保存新一轮记录，待重新确认后再规划。

## 3. 需求状态与保存

`my-requirements` 等名称是用户通过 `--session` 手动指定的目录名；不指定时，新需求会话使用 `discovery-随机标识`。忘记路径时，在 Astra 根目录执行：

```powershell
python -m astra_designer --session --list
python -m astra_designer --session -l
```

也支持 `python -m astra_designer chat --list`。列表显示名称、类型、状态、摘要、最近保存时间（带本机时区）、完整路径和恢复命令，按时间从新到旧排序，不调用模型。

默认搜索 `workspace/designs` 下的会话，不包含内部规划子会话。自定义保存位置用 `python -m astra_designer --session "D:/我的会话" -l` 搜索该目录。列表不会自动发现其他磁盘上的任意路径；损坏或不可访问的记录会显示提示。时间取会话文件最后修改时间，不代表首次创建时间。

| 状态 | 含义 |
|---|---|
| `exploring` | 正在澄清需求 |
| `awaiting_confirmation` | 关键类别齐全且无阻塞事项，等待用户审阅 |
| `confirmed` | 用户显式确认当前版本 |
| `failed` | 模型调用或记录校验失败，可 `/retry` |
| `budget_exhausted` | 旧版状态，恢复时转为 `failed`，可直接重试 |

确认前所有条目均是待确认的解释；用户原文引用证明其出处，不证明模型的解释已经正确。

```text
会话目录/
├── discovery.json             权威会话状态、问答、调用数和规划记录
├── requirements.yaml          当前需求视图（JSON 形式的合法 YAML）
├── requirements-history/      每一版需求记录
├── confirmed-0003.json         曾确认的不可变版本快照
└── plans/                     不同版本对应的独立蓝图规划会话
```

当前需求必须涵盖目标、参与者、输入、输出、规则、约束、范围、验收及场景。偏好可选。非阻塞未决事项可以保留，但会显示给用户；不会静默转为确定规则。

恢复：

```powershell
python -m astra_designer chat --session workspace/designs/payroll-discovery
```

`/resume 路径` 也可以切换到已保存的需求会话。旧版 `session.json` 会话通过 CLI 的 `--session` 自动使用旧版对话。

## 4. 从共识进入蓝图

框架偏好属于独立技术配置：`/frameworks` 查看支持，`/framework auto` 或 `/framework astra.configured@1` 设置默认值。更换框架保留业务确认，重新 `/plan` 检查实现。详见 [执行框架适配说明](执行框架适配使用说明.md)。

`/plan` 将确认的需求快照交给现有规划器。生成的蓝图包含：

- `requirements`：需求版本、内容摘要及用户确认记录。
- `traceability`：每个 `REQ-xxx` 对应的蓝图位置。

输入需求必须引用输入，处理规则必须引用阶段或 Agent，验收需求必须引用验收项。未知需求、缺失映射和不存在的路径会使校验失败。生成项目中的蓝图也保留这些内容，并纳入生成文件摘要。

业务团队必须有明确的输入和交付成果。方案阶段除团队方案外，还会给出输入规范 `task_input`（至少一项必填资料）和交付物清单 `deliverables`：每项交付物有 `DEL-xxx` 标识、名称、内容说明、形式和对应需求。形式有三种：`file`（文件，列出 txt/md/docx/pdf/csv/xlsx 格式）、`data`（运行记录中的数据）、`action`（对外部状态的改变，如清理文件、发送通知，此时 `evidence` 写明如何验证）；每项 output 需求都必须有交付物，描述中不能出现“待定”“运行时决定”，每次运行才确定的篇幅、格式等写成 `task_input` 字段。`/requirements` 和方案展示都会列出交付成果，确认的是这份输入与交付契约。规划时每项交付物都要在 `traceability` 中映射到检查它的验收项：文件须由 `document.write@1`（txt/md/docx/pdf）或 `table.write@1`（csv/xlsx）写出并逐一验收格式，数据须检查 `/data/<数据键>`，动作须由真正执行它的 Agent（`fs.cleanup@1`、`http.request@1` 或待接入节点）产出执行记录并检查该记录。旧会话缺少交付物清单时，`/plan` 会先补齐并请你重新确认。生成项目的 README 会列出交付成果。

交付物是小说、文章、报告等文档时，需求阶段会确认文件格式（txt、md、docx、pdf，可多选，或在接单资料中增加 `output_format` 由每次运行选择）。规划器用内置能力 `document.write@1` 把上游文本写入本次运行的输出目录（`output/runs/<运行ID>/`），docx 无需额外依赖；`astra run` 结束时会列出生成的文件路径。没有文件需求时，业务结果保存在该目录 `state.json` 的 `data` 中。规划摘要提到“待接入”能力而蓝图中没有对应待接入节点时，校验会要求模型补上节点或删掉这一说法。

结构追溯不等于业务语义已经验证。系统不能仅凭引用存在，就证明某个公式正确实现了规则；需要审阅蓝图、场景和业务验收结果。

如果规划器发现需求仍需澄清，会返回问题并撤销当前确认；直接回答问题，重新整理与确认。缺少实现的部分会生成待接入节点，接入前运行到该步骤会暂停；需求无法表达时会返回澄清问题。需求文档始终保留，不会自动缩减需求。

## 5. 运行资料、样例与当前边界

每次运行的资料由确认的 `task_input` 定义，不需要在设计阶段提供样例文件。需要每次提交 Excel 或 CSV 时，`task_input` 用一个字符串字段填写文件路径，项目通过 `table.read@1` 读取、`table.compute@1` 精确计算；提交 txt、md、docx、pdf 文档时用 `document.read@1`，网页用 `web.fetch@1`；“检查不通过就返工”用 `flow.route@1` 跳回并限制次数；清理本机文件用 `fs.scan@1` 扫描、`fs.cleanup@1` 处理（默认只试算，可移入隔离目录，非试算模式必须先确认，且只能在声明的目录内操作）；交付文件由 `document.write@1`（txt、md、docx、pdf）或 `table.write@1`（csv、xlsx）写出；已知地址的 HTTP 接口用 `http.request@1` 调用；长文本按大纲用 `llm.map@1` 逐章生成；需要“继续上次的工作”时用 `state.load@1` / `state.save@1` 在项目本地保存状态。模型判断（如一致性检查）直接用 `llm.transform@1`，不算外部服务。其他外部服务会生成待接入节点，项目可以生成和接单，接入前运行到该步骤会暂停，前面的步骤照常完成。

`/input` 可以为客户反馈示例流程添加固定的 JSON 样例资源，属于可选功能。样例内容与原始绝对路径不会在探索阶段发送给模型；添加或替换样例会清除当前规划，保留需求确认。

规划状态为 `ready` 后，可以 `/show`、`/generate`、`/run`。新对话保存实际生成路径，自定义生成目录在恢复会话后仍可使用。生成目录必须不存在，最后一级目录名必须匹配项目名。

## 6. 分步生成与失败恢复

需求澄清每轮最多 2 次模型调用。进入方案阶段后，按需求核对、团队角色、输入规范三步生成，每步仅返回对应的小型 JSON，通过后自动进入下一步。每步最多调用 2 次（生成及一次修复），完整方案最多 6 次；恢复时只运行剩余步骤。调用次数增加但每次输出更小，实际总 Token 不保证减少。不再限制会话累计调用次数；调用前记录次数，模型错误或中断也计入统计。网络、认证及响应截断等模型错误不会自动重试，需排查后手动继续。

三个步骤均可随时提出业务澄清问题。团队及输入规范步骤使用独立的 `clarification` 响应分支，说明缺失信息或需要用户决定的取舍，每次最多两个具体问题。合法提问立即转为等待用户回答，不视为生成失败，不自动重试，也不能确认半成品。需求和前序方案草稿会保存，直接回答即可；恢复后结合答案重新核对需求及受影响的方案，再自动继续。诊断状态为 `awaiting_user`。模型应自行处理内部字段错误，不应重复询问已有答案或用户已授权团队决定的事项；实际接单时才需要的素材留在输入规范中收集。

内部校验失败时，设计器会携带失败候选和具体校验反馈定向修复，保留有效需求与方案内容。校验错误会指明方案、角色及需核对字段，不要求用户解释内部字段。同一步两次调用后仍失败则保存进度，界面直接显示一句失败原因（例如输出被截断、服务请求失败或格式检查未通过），`/requirements` 顶部也会显示；详细错误保存在逐次调用诊断中（`section` 指明步骤）。完整候选不超过 200000 字符时会保留供 `/retry` 继续修复；超过此大小则依据已有需求和错误反馈重新生成，不使用截断候选。已通过步骤单独保存，不覆盖已接受记录；完整组装后仍执行原有结构、来源和业务约束校验。用户提交新需求会清除分步草稿；修复成功后也会清除草稿。旧版会话可直接恢复，新一轮方案自动使用分步生成。

`/retry` 重试失败的需求探索，`/continue` 保留为同义命令，无需增加额度。旧版额度耗尽的会话可以直接恢复并重试，历史调用数不重置。每个会话的蓝图规划请求次数上限由 `.astra-designer/settings.json` 的 `max_plan_calls` 决定（默认 6，`null` 表示不限，也可用环境变量 `ASTRA_DESIGNER_MAX_PLAN_CALLS` 覆盖）；模型截断、连接失败等模型侧错误不计入，修改需求不会自动重置计数。

模型响应未正常结束时，逐次调用诊断文件的 `error.details` 会记录 `finish_reason`、是否流式响应、失败阶段，以及是否出现拒绝、工具调用或旧版函数调用。`length` 表示输出达到上限，`content_filter` 表示服务返回内容过滤标记，`missing` 表示未收到结束原因；非标准值记为 `unknown`。`stage=eof_before_done` 表示连接读到末尾但未收到 `[DONE]`。不保存拒绝正文、工具参数或原始错误响应。此信息也用于输入规范补全的失败诊断；已有失败记录无法追溯补齐，需重试产生新记录。

### 会话目录中的文件

每类信息只保存一份权威记录，其余文件引用它：

| 文件 | 内容 |
|---|---|
| `discovery.json` | 会话状态、对话记录（每轮带时间；“继续”等命令展开的发言标记 `command`，不作为需求依据）、当前需求、确认记录、最近一次规划的摘要 |
| `requirements.yaml` | 当前需求的可读 YAML，含每条需求的用户原话依据 |
| `requirements-history/<修订号>.json` | 每个修订号的完整需求 |
| `confirmed-<修订号>.json` | 确认记录（时间、摘要、所选方案），需求正文指向对应的 history 文件 |
| `diagnostics/call-*.json` | 每次需求调用：开始时间、模型设置（模型、输出上限、思考设置等，不含密钥）、请求规模、思考与正文字符数、用量、耗时、回复与错误 |
| `plans/<规划ID>/session.json` | 规划会话，含用于生成蓝图的完整需求快照 |
| `plans/<规划ID>/revisions/*/attempts.json` | 每次规划调用的同类记录；输出被截断时，已收到的部分回复保存为 `response-*.json`（`complete: false`） |
| `cli-history.json` | 终端实际输入与显示文字，供 `/export` 使用 |

模型输出被截断时，界面会给出输出上限以及思考、正文各自的字符数；思考占多数时建议把 `reasoning_effort` 设为 `none`。蓝图是结构化输出，通常不需要思考。

## 7. 非交互入口与 API

```powershell
python -m astra_designer explore --session workspace/designs/example --message-file goal.txt
python -m astra_designer explore --session workspace/designs/example --message-file answer.txt
python -m astra_designer explore --session workspace/designs/example --action show
python -m astra_designer explore --session workspace/designs/example --action confirm --revision 2
python -m astra_designer explore --session workspace/designs/example --action plan
```

文件为 UTF-8；版本号以实际结果为准。`show`、`confirm` 无需模型配置。文件命令目前没有样例添加参数，可用交互 `/input` 或 API 提供样例。

```python
from astra_designer import explore_requirements, plan_requirements

state = explore_requirements("描述业务需求", "workspace/designs/example")
# 持续提供回答，直到 awaiting_confirmation；用户审阅后才能调用确认操作。
state = explore_requirements(None, "workspace/designs/example",
                             action="confirm", revision=state["revision"])
result = plan_requirements("workspace/designs/example")
```

以上确认语句仅展示 API，用于承接用户显式确认，不应自动接在模型回答后执行。

## 8. 代码入口与验证

`discovery/pipeline.py` 控制流程；`discovery/context.py` 构建模型上下文；`contracts/requirements.py` 校验记录和来源；`discovery/validation.py` 校验蓝图追溯；`resources/discovery_prompt.md` 定义探索方法。

新增离线测试覆盖无文件探索、澄清历史、显式确认、修订失效、虚构来源、预算恢复、项目隔离、需求覆盖，以及从确认到生成和运行的完整链路。测试采用模型替身，不代表真实模型的需求理解质量已得到验证。
