# Astra 引擎架构说明

本文档仅描述 Astra 引擎。业务项目的 Agent、数据、提示词、工作流和模型配置由项目自身维护，不属于引擎实现。

## 1. 分层模型

```text
Astra Public API
└── astra/：稳定的公开入口

Engine Implementation
├── 项目加载：astra_core/project.py
├── 运行 API：astra_core/engine.py
├── 核心编排：astra_core/core/
├── 运行时配置与 Hook：astra_core/runtime/
├── 扩展系统：astra_core/extensions/
├── 工具协议：astra_core/tools/
├── SDK Adapter：astra_core/adapters/
├── 内置 Agent：astra_core/agents/default/（选择等通用 Agent）
└── 通用服务：astra_core/services/（http_client、files、text、console）

Business Project
├── project.yaml
├── agents/
├── configs/workflow.yaml
├── tools/
├── prompts/
├── data/
└── output/
```

引擎不直接导入某个业务包，也不保存隐式的全局当前项目。业务项目通过 `project.yaml` 被加载；运行时输出被隔离在项目自身的 `output/runs/<run_id>/`。

## 2. 加载与运行 API

```python
from astra import engine

runtime = engine.load("business/my_project/project.yaml")
runtime.inspect()
state = runtime.run()
runtime.run_stage("stage_id")
runtime.resume(state["data"]["run"]["id"])

engine.inspect("business/my_project/project.yaml")
engine.resume("<run_id>")
```

`engine.load()` 返回不可变的 `ProjectRuntime`，其中持有已解析的 `BusinessProject`。每次 `run()` 与 `run_stage()` 创建新的运行会话；`resume()` 使用 `run.json` 和 `state.json` 恢复指定会话。

`inspect()` 校验项目资源、扩展声明与工作流结构。若可选 SDK 缺失，它仍返回静态工作流结构，并在返回结果的 `runtime.status` 中标记 `dependency_missing`；实际执行时才会要求该依赖。

## 3. 项目清单

`project.yaml` 是引擎与业务项目之间的唯一加载契约，核心字段如下：

| 字段 | 作用 |
| --- | --- |
| `name` / `package` | 项目名称与可导入 Python 包名。 |
| `workflow_config` | 相对项目根目录的工作流配置路径。 |
| `tools_dir` | 业务工具目录。 |
| `hooks_dir` | 可选业务 Hook 目录；由 `project_hooks` 自动发现。 |
| `paths` | `data`、`prompts`、`output` 等资源目录。 |
| `extensions` | 按顺序加载的扩展模块。 |
| `distribution` | 版本、引擎要求和可分发资源元数据。 |
| `config_module` / `llm_config` | 可选模型配置入口。 |
| `initial_task` | 默认任务。 |

相对路径全部以 `project.yaml` 所在目录为基准解析，因此业务项目可以被复制或打包而不依赖仓库根目录。

## 4. Stage -> Agent -> Tool 三层业务结构

`Stage -> Agent -> Tool` 是 Astra 的通用业务执行模型，不绑定任何具体项目：

```text
OrchestratorAgent
└── Stage：一个可独立观察、重跑和路由的业务子目标
    └── Agent：完成明确领域处理或人机交互的执行单元
        └── Tool：数据读取、计算、外部调用等确定性能力
```

| 层级 | 职责 | 边界 |
| --- | --- | --- |
| `Stage` | 组织同一业务子目标下的 Agent，定义阶段输入输出、默认下一跳与阶段重跑边界。 | 业务目标发生切换，或需要独立监控、重跑、沉淀产物时，应拆分 Stage。 |
| `Agent` | 读取共享状态并产出结构化业务结果。 | 一个 Agent 只承担一类决策、生成、校验或交互职责。 |
| `Tool` | 提供可复用、可测试的底层确定性能力。 | Tool 不负责阶段路由，不直接修改编排流程。 |

`OrchestratorAgent` 在 Stage 间路由，在 Stage 内调度 Agent；Agent 通过 Adapter 调用 Tool。Hook 不属于业务层级，而是贯穿各生命周期的横切扩展点。

## 5. 工作流编排

`workflow.yaml` 声明 Agent 包、编排选项、Agent 角色和阶段：

```yaml
runtime:
  agent_packages: [business.my_project.agents]

orchestrator:
  max_retries: 3
  hook_profile: standard
  flow: {type: serial}
  stage_routing: {init: prepare, prepare: execute, execute: end}

agents:
  - role: worker
    class: WorkerAgent
    max_retries: 2

stages:
  - stage_id: prepare
    agents: [worker]
    next_stage: execute
    flow: {type: serial}
```

`OrchestratorAgent` 负责阶段路由、阶段内 Agent 调度、重试、状态合并、执行记录和报告。Agent 必须继承 `BaseAgent`，并返回 `dict`：

```python
{
    "status": "success",
    "data": {"domain_result": {}},
    "next_stage": "optional_stage_id",
    "next_role": "optional_role_in_current_stage",
}
```

`data` 会合并进 `state["data"]`。业务字段由业务项目定义；引擎只保证该共享数据区、控制字段和执行记录的通用语义。

当前内置可执行工作流类型为 `serial`。`sync` 与 `async` 是预留接口；可通过编排器注册新的 flow handler 扩展。

## 6. Extension API

Hook、Tool 和 SDK Adapter 统一为 Extension。扩展模块导出：

```python
def register_extension(context):
    ...
```

`ExtensionContext` 提供：

- `project`：已加载的业务项目。
- `orchestrator`：当前会话的编排器。
- `output_dir`：当前会话的独立输出目录。
- `provide(name, value)` / `require(name)`：扩展之间的显式服务传递。

引擎按 `project.yaml` 的 `extensions` 顺序注册扩展。常用内置扩展：

| 扩展 | 职责 |
| --- | --- |
| `astra_core.extensions.project_tools` | 导入业务工具并注册 `ToolSpec`。 |
| `astra_core.extensions.project_hooks` | 按稳定顺序加载 `hooks/` 中导出 `register_hooks(context)` 的模块。 |
| `astra_core.extensions.workflow_artifacts` | 注册原始 Agent 输出、Hook 事件和报告持久化。 |
| `astra_qwen.extension` | 将已注册工具适配给 Qwen Agent。 |

工具 Adapter 应位于工具加载扩展之后；`project_hooks` 用于常规业务 Hook。第三方 Adapter、服务客户端及其他非约定型能力仍通过 `extensions` 显式声明。

## 7. 生命周期与产物

Hook 生命周期包括 `PreStage`、`PostStage`、`PreAgent`、`PostAgent`、`PreToolUse`、`PostToolUse`、`OnError` 与 `SessionEnd`。Hook 可以返回 `HookResult`，将数据补丁写入共享状态、写入全局状态补丁或阻断执行。

标准运行产物位于：

```text
output/runs/<run_id>/
├── run.json
├── state.json
├── orchestrator.log
├── orchestrator_report.json
├── orchestrator_structure.png
├── hook_events.json
└── agents/<stage>/<role>/attempt_<n>_raw.json
```

`run.json` 保存项目来源、会话状态、摘要与产物索引；`state.json` 保存可恢复的工作流状态。运行日志与报告不会写入业务源代码目录之外。

## 8. 扩展与约束

- 新 Agent 应放在业务项目的 `agents/` 中，并通过 `workflow.yaml` 注册，不应修改引擎入口。
- 新业务工具应注册框架无关的 `ToolSpec`；具体模型 SDK 支持由 Adapter 提供。
- 新横切能力应实现为 Extension 或 Hook，避免侵入业务 Agent。
- `state["data"]` 是动态共享数据区。业务项目应维护稳定、避免冲突的字段命名。
- 运行会话仅在同一项目输出根目录中恢复；全局 `engine.resume(run_id)` 要求本地 run ID 唯一。
